Trees are one of the most versatile and widely used data structures in computer science. A \index{tree}\newterm{tree} is a hierarchical data structure consisting of nodes, where each node has a value and a set of references (\newterm{edges}) to its child nodes. The node at the top of the hierarchy is called the \index{root}\newterm{root}, and nodes with the same parent are called \newterm{siblings}, as seen in Figure~\ref{fig:tree1}.\\

Trees are a special kind of graph, a data structure comprised of nodes and edges. A tree is a graph with two properties:
\begin{itemize}
  \item The graph is connected, such that there exists a path between every pair of nodes
  \item The graph is acyclic; no cycles exist in the graph
\end{itemize}
With this comes the caveat that the number of edges in a tree is $\text{edges} = n - 1$, where $n$ is the number of nodes in the tree. This is because a tree with $n$ nodes must have exactly $n-1$ edges to maintain its connected and acyclic properties. If there were more than $n-1$ edges, it would create a cycle, violating the acyclic property. If there were fewer than $n-1$ edges, it would not be fully connected, violating the connected property.

Less formally, a \newterm{forest} is a collection of multiple trees (may be disconnected), and a \newterm{tree} is a forest with only one tree. Lots of agricultural terms in this chapter!

Trees have a unique structural property: between any two nodes, there exists exactly one simple path. This follows directly from the fact that trees are both connected and acyclic. As a result, there is only one way to move from a start node to an end node.

Although trees are often drawn with a root at the top, this is a matter of convention. Any node in a tree can be chosen as the root, and doing so induces a hierarchical structure in which edges are interpreted as parent-child relationships.

Once a root is selected, every node (except the root) has exactly one parent, and zero or more children. Because of this relationship, any randomly selected node can form a tree (we call this a \index{subtree}\newterm{subtree}, consisting of the node and all its descendants), making the tree structure \newterm{recursive}. A function that works on a tree can call itself on each subtree, and each call handles a smaller tree.

Nodes with no children are called, as you would expect, \newterm{leaves}, as they are the outermost node of a tree. The \index{depth}\newterm{depth} of a chosen node is the number of edges from the \emph{root} to that node, and the \index{height!of a tree}\newterm{height} of a tree is the maximum depth among all nodes. Equivalent to the height of a tree is the maximum number of edges from the \emph{root} to any leaf. You may see the \newterm{level} of a node referred to as the number of edges from the \emph{root} to that node, similar to depth. By convention, the level and depth of the root is 0. See Figure~\ref{fig:tree2}.

Some more relevant terminology you may encounter in the context of trees:
\begin{itemize}
  \item \newterm{Path}: A sequence of nodes where each adjacent pair is connected by an edge. This can be used to show the idea of how to get between two nodes in a tree, for example, between two cities in a flight path network.
  \item \newterm{Ancestor}: A node that lies on the path from the root to a given node. This is done by repeatedly traversing from a child node to a parent node until the selected node is reached.
  \item \newterm{Descendant}: Any node you can reach from a given node by repeatedly moving from a parent to one of its children. A node's descendants are everything in its subtree except itself.
\end{itemize}

\section{Binary Trees and Binary Search Trees}\index{binary search tree}\index{binary tree}
The most common type of tree is the \newterm{binary tree}, where each node has \emph{at most} two children, referred to as the \newterm{left child} and the \newterm{right child}. Binary trees are widely used in various applications, including expression parsing, binary search trees, and heaps.

Let us put this idea into practice. Recall our binary search implementation from the recursion chapter. Given a chosen word and a sorted list of words, such as a dictionary, we can find the page of the chosen word by repeatedly dividing the available pages in half and comparing the elements on the page to the chosen word. This is much easier than, for example, going through every single page and checking if the word is on that page.

Say we wanted to represent our dictionary as a tree that we could recursively binary search through. For simplicity, we will limit our words to \texttt{mango}, \texttt{apple}, \texttt{pear}, \texttt{banana}, \texttt{anagram}, \texttt{peony} and \texttt{peach}. These 7 words form a binary tree of height 2, as seen in Figure~\ref{fig:bst1}. We select the word \texttt{mango} as the root as it is the middle word after sorting alphabetically.

Similar to binary search, we can find any word in the tree by starting at the root and comparing the target word to the current node's word. If the target word is less than the current node's word, we move to the left child; if it is greater, we move to the right child. We repeat this process until we find the target word or reach a leaf node, which tells us that the target word is not in the tree. This structure allows us to cut the available words in half with each step in the tree we go.

What if we want to insert into a binary search tree? We must complete four actions:
\begin{itemize}
  \item Find the correct location for the new node.
  \item Create and insert the node at that location,
  \item Connect it to its respective parent(s).
  \item Ensure the BST properties are maintained.
\end{itemize}

The new node is always a leaf. We find its location the same way we search: at each node, go left if the new word comes first alphabetically, and go right if it comes later.

Let us say, on our tree above, we want to add \texttt{orange} to the tree. \texttt{orange} comes after \texttt{mango}, so we go right to \texttt{pear}. \texttt{orange} comes before \texttt{pear}, so we go left to \texttt{peach}. \texttt{orange} comes before \texttt{peach}, and \texttt{peach} has no left child. So we make \texttt{orange} the left child of \texttt{peach}.

\begin{Exercise}[title={Insert into a Search Tree}, label={ex:bst_insert}]
Using the tree in Figure~\ref{fig:bst1}, insert \texttt{kiwi}. Write the sequence of words you compare \texttt{kiwi} with, and say where the new node goes.
\end{Exercise}
\begin{Answer}[ref={ex:bst_insert}]
\texttt{kiwi} comes before \texttt{mango}, so go left to \texttt{apple}. \texttt{kiwi} comes after \texttt{apple}, so go right to \texttt{banana}. \texttt{kiwi} comes after \texttt{banana}, and \texttt{banana} has no right child. So \texttt{kiwi} becomes the right child of \texttt{banana}.
\end{Answer}

\section{File Structures and File System Hierarchies}\index{file system!hierarchy}
Computers have always needed a way to store and organize data. Prior to computers, many systems of organization were used to store physical data, such as filing cabinets, libraries, and warehouses.

These systems often had a hierarchical structure, with a top-level category that branched out into subcategories, with these subcategories further branching out into more specific categories, and so on.

For example, a library might have two top-level categories: \texttt{fiction} and \texttt{non-fiction}. Within the category \texttt{non-fiction}, you may find \texttt{psychology}, \texttt{biographies}, \texttt{autobiographies}, \texttt{self-help}, \texttt{journalism} books, or even \texttt{nature guides}. Under the category \texttt{fiction}, you may find \texttt{romance}, \texttt{classics}, \texttt{crime}, \texttt{science fiction}, \texttt{thriller}, or \texttt{fantasy} novels. Of course, these sub-genres can have even further categorizations too.

A hospital may have patient records categorized by first letter of last name, and then sorted alphabetically from there.

With the development of the computer, sorting these types of hierarchical data became easy with the concept of directories. A \index{directory}\newterm{directory}, also called a \newterm{folder}, is a categorical way of organizing data (for example, by storing files or other subdirectories). We will stick to the more technical term of directories, however, any time you create a folder on your computer, you are making a \emph{directory}. The name comes from how, in the twentieth-century, many phone books were referred to as telephone directories.

This structure naturally fits into the tree data structure:
\begin{itemize}
  \item The \textbf{root} of the tree is the top-level directory (\texttt{/} on Linux/Unix\footnote{There is a very helpful video in Linux File Systems in your digital resources. Check it out!} systems or \texttt{C:\textbackslash} on Windows).
  \item A \textbf{node} naturally fits the idea of either \emph{directories nodes} or \emph{files nodes}.
  \item A \textbf{directory node} may have children, where its children are subdirectories or files.
  \item A \textbf{file node} is a \textbf{leaf}, meaning it has no children.
\end{itemize}

The \textbf{path} to a file describes the unique sequence of directories from the root to that file.

\section{Balanced Trees: AVL and Red-Black}\index{balanced tree}

A binary search tree is fast only if it is bushy. Insert the words
\texttt{anagram}, \texttt{apple}, \texttt{banana}, \texttt{mango},
\texttt{peach}, \texttt{pear}, \texttt{peony} \emph{in alphabetical order},
and each new word goes to the right of the last one. The ``tree'' is just
a chain of 7 nodes with height 6, and searching it is no faster than
reading a list from the top. The same seven words in Figure~\ref{fig:bst1}
have height 2.

A \newterm{balanced} tree keeps its height close to $\log_2 n$ no matter
what order the data arrives in. Two famous designs:

\begin{itemize}
\item An \index{AVL tree}\newterm{AVL tree} (named for its inventors,
Adelson-Velsky and Landis, 1962) requires that at every node, the heights
of the left and right subtrees differ by at most 1. After an insertion
breaks that rule, the tree performs a \newterm{rotation}\index{tree
rotation}: it lifts a child up into its parent's place, shifting a few
pointers. A rotation keeps the left-to-right (alphabetical) order intact
while making the tree shorter.
\item A \index{red-black tree}\newterm{red-black tree} colors every node
red or black and enforces a few rules: the root is black, a red node never
has a red child, and every path from a node down to an empty spot passes
through the same number of black nodes. Together, these rules guarantee
that no path is more than twice as long as any other. Red-black trees are
slightly less strictly balanced than AVL trees but need fewer rotations,
which is why C++'s \texttt{std::map} and Java's \texttt{TreeMap} use them.
\end{itemize}

Either way, searching, inserting, and deleting take $O(\log n)$ time: a
million items need only about 20 levels.

\begin{Exercise}[title={How Tall?}, label={ex:tree_height}]
\begin{enumerate}
\item A binary tree with every level completely full has height $h$. How many nodes does it have?
\item About how tall is a balanced binary search tree holding 1,000,000 words? How tall could an unbalanced one be?
\end{enumerate}
\end{Exercise}
\begin{Answer}[ref={ex:tree_height}]
\begin{enumerate}
\item Level $k$ has $2^k$ nodes, so the total is $1 + 2 + 4 + \cdots + 2^h = 2^{h+1} - 1$. (Height 2 gives 7 nodes, like Figure~\ref{fig:bst1}.)
\item Since $2^{20} \approx 1{,}000{,}000$, a balanced tree is about 20 levels tall. If the words arrive in sorted order with no balancing, the tree is a chain with height 999,999.
\end{enumerate}
\end{Answer}

\section{B-Trees, Tries, and Suffix Trees}

Not every tree is binary.

A \index{B-tree}\newterm{B-tree} lets each node hold many keys (often
hundreds) and have many children. Reading from a disk is slow, but reading
a big chunk is not much slower than reading a small one. So databases and
file systems store each node in one disk block. A B-tree holding a billion
records may be only 4 or 5 levels deep, which means only 4 or 5 slow disk
reads per lookup.

A \index{trie}\newterm{trie} (from re\emph{trie}val, usually pronounced
``try'') stores words letter by letter. Each edge is a letter, and each
path from the root spells the start of a word. Words that share a prefix
share a path: \texttt{car}, \texttt{cart}, and \texttt{cat} all start down
the \texttt{c}--\texttt{a} branch. To autocomplete \texttt{ca}, your phone
walks two edges and lists everything below that node.

A \index{suffix tree}\newterm{suffix tree} is a compressed trie of all the
suffixes of one long string. For the string \texttt{banana}, those are
\texttt{banana}, \texttt{anana}, \texttt{nana}, \texttt{ana}, \texttt{na},
and \texttt{a}. Every substring is the beginning of some suffix, so you can
check whether any pattern appears in the text by walking down from the
root, in time proportional to the length of the pattern, not the text.
Biologists use suffix trees to search DNA, where the ``text'' can be
billions of letters long.

\begin{Exercise}[title={Build a Trie}, label={ex:trie}]
Draw a trie for the words \texttt{to}, \texttt{tea}, \texttt{ten}, and
\texttt{in}. How many nodes does it have, counting the root?
\end{Exercise}
\begin{Answer}[ref={ex:trie}]
The root has two children, \texttt{t} and \texttt{i}. Under \texttt{t} are
\texttt{o} (ending \texttt{to}) and \texttt{e}; under \texttt{e} are
\texttt{a} (\texttt{tea}) and \texttt{n} (\texttt{ten}). Under \texttt{i}
is \texttt{n} (\texttt{in}). That is the root plus 7 letter nodes, 8 in
all. The shared prefix \texttt{te} is stored only once.
\end{Answer}
